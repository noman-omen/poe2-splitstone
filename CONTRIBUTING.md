# Contributing to Splitstone

Thanks for helping. Bug reports, route corrections and small focused pull requests are all welcome. For questions and ideas, use [Discussions](https://github.com/noman-omen/poe2-splitstone/discussions).

## Run it locally

The web app has no build step. Open `index.html` in a browser, or serve the folder (some features, such as the Python helper's auto-split, expect `http://`):

```sh
python3 -m http.server 8765 --bind 127.0.0.1
# open http://127.0.0.1:8765/
```

Desktop app (Electron, Node 22 or newer):

```sh
cd desktop
npm ci
npm start
```

## Tests

CI runs these on every release tag. Run them before opening a PR:

```sh
npm ci && npm run lint           # repo root: eslint
cd desktop
npm ci
npm test                         # desktop unit tests, plus tests/*.test.js
xvfb-run -a npx electron . --smoke --no-sandbox   # Linux; prints SMOKE_OK
```

The browser tests use Playwright and need the app served on port 8765 (or `TRACKER_URL`):

```sh
pip install playwright && python3 -m playwright install chromium
python3 -m http.server 8765 --bind 127.0.0.1 &
python3 tests/smoke_test.py
python3 tests/layout_test.py
python3 tests/overlay_test.py
python3 tests/overlay_theme_test.py
python3 tests/classes_test.py
python3 tests/security_test.py
python3 tests/autosplit_test.py
python3 tests/endgame_test.py
python3 helper/test_helper.py
```

Run the suite for the area you touched; the other `tests/*_test.py` files cover dialogs, ghosts, levels, imports and storage. Tests write screenshots to `test-output/`. `SPLITSTONE_UPDATE_SHOTS=1` refreshes the README images in `screenshots/`; only do that when the UI change is intentional.

`scripts/record_demo.py` re-records `screenshots/demo.gif` (needs ffmpeg). CI doesn't run it.

## Code style

- `npm run lint` must pass (`eslint.config.js`).
- Plain browser JavaScript, no framework and no bundler. Match the style of the file you're in.
- The Python helper uses the standard library only.
- Comments explain why, not what.

## Pull requests

- Keep them small: one fix or feature per PR. Split refactors from behaviour changes.
- Link the issue, say how you tested it, and add screenshots for UI changes.
- Add a line to `CHANGELOG.md` under `## Unreleased` for anything a user will notice.

## Route data

| File | What it holds |
| --- | --- |
| `data/campaign.js` | The campaign route (`window.CAMPAIGN_DATA`) |
| `data/class_notes.js` | Playable classes, ascendancies and class-specific notes |
| `data/gear_checkpoints.js` | Weapon, gem and vendor checkpoints along the route |
| `data/endgame.js` | Endgame milestones |
| `data/tools.js` | Links on the Tools tab |

`data/campaign.js` is generated by `scripts/build_data.py` from the maintainer's route source. Its shape is `groups` (an act or interlude, for totals) → `sections` (a timed segment; Interlude 2 has two) → `zones` → `steps`. Each step has an `id`, `zone`, `level`, `objective`, optional `waypoint`, `area` (the Client.txt area id used for auto-split), `modes` (`normal`, `fast`), `hints`, `fastTips`, `details`, `skip`, `rewards` and `warning`.

For route fixes, open a [route correction](https://github.com/noman-omen/poe2-splitstone/issues/new?template=route_correction.yml) with the patch you checked, or send a PR that edits `data/campaign.js` directly and say so in the PR; the maintainer carries it into the source. Don't change step `id`s: saved runs and splits refer to them.

## Game rules

Splitstone stays within Grinding Gear Games' terms of service. It reads the game's `Client.txt` log and nothing else: no memory reading, no packet inspection, no injected input or automation of any kind. PRs that cross that line won't be merged.
